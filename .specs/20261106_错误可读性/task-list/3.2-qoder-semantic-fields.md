# 3.2 qoder 解析扩字段与语义透传

- 所属任务组：T3. 采集与落盘
- 硬前置：1.1、2.1、3.1

## 目标

让 `runQoder` 在失败时把 stdout `result` 行里的语义字段读出来、归类、并分别送到诊断文件、用户文案与调用方——这是修复两次事故根因的核心改动。

**关键设计决策 1：判定顺序完全不动。** `killedByTimeout` → 空输出 → `!parsed` → `code !== 0` → `is_error` → 成功，保持一期顺序。语义 class 只决定**用户文案**，传输层 kind 仍如实记录，两者正交。改顺序会破坏一期正确性属性 5 / 7 与既有单测。

**关键设计决策 2：新增 `errorDetail` 承载原文，`error` 只放中文模板。** `service.ts:591` 的续接降级正则依赖原文，若直接把原文从 `error` 里拿掉，该重试会静默失效（4.1 负责迁移调用点）。分成"对外文案"与"对内信号"两个字段，才能让需求 1.5 与 N1 同时成立。

**边界条件**：`timeout` / `spawn` / `empty` / `parse` 四类**不传** `semantic`——它们要么没有 `parsed`，要么进程被 SIGKILL，语义字段不可信。这四类 `errorClass` 由 `classifyQoderError({})` 得到 `'unknown'`，文案沿用一期。

## 实现要点

- 修改 `src/bridge/qoder.ts`：
  - `ParsedResult` 新增 4 个字段，类型为 `unknown`（原样透传，不做类型断言，归一化交给 `classifyQoderError`）：`stop_reason` / `error_code` / `error_message` / `errors`。上游另有 `subtype`，但无消费方，不透传。
  - `parseResult` 的解析策略**完全不变**（整段 + 尾部 200 行、`type === 'result'` 判定、`PARSE_WHOLE_MAX` / `PARSE_TAIL_LINES` 常量、5MB 缓冲上限），只在返回对象里多带这 4 个字段。
  - `QoderRunResult` 新增 3 个可选字段（向后兼容）：`errorClass?: QoderErrorClass`、`errorCode?: string`、`errorDetail?: string`。
  - `settleFailure` 的 `opts` 新增 `semantic?: QoderSemanticFields`；函数体内调用 `classifyQoderError(opts.semantic ?? {})`，把结果分别送给：
    - `writeDiagnostic({ …, errorClass, errorCode })`
    - `buildUserErrorReply({ …, errorClass })`
    - `resolve({ …, errorClass, errorCode, errorDetail: classification.detail })`
  - `finalize` 的 `exit` 与 `is_error` 两个分支透传 `semantic`，取值为 `{ errorCode: parsed.error_code, errorMessage: parsed.error_message, errors: parsed.errors, stopReason: parsed.stop_reason, isError: parsed.is_error, result: parsed.result }`。
  - `timeout` / `spawn` / `empty` / `parse` 四个分支**不传** `semantic`。
- 扩充 `test/fixtures/fake-qodercli.mjs`，**直接使用真实诊断文件里的 JSON 结构**（`~/.local/state/qoder-wechat-bridge/logs/diagnostics/`），新增 7 个 mode（下表 5 个取真实样本，另 2 个为边界组合，见设计 8.4）：
  | mode | 关键字段 | 退出码 |
  | --- | --- | --- |
  | `quota-110` | `is_error:true`、`stop_reason:"stop_sequence"`、`error_code:110`（**number**）、`error_message:"Billing daily count exceeded"`、`errors:["You've reached your daily usage limit for Chat. Come back tomorrow to continue working with me. Report Issue (input /feedback)"]`、`result:""` | 1 |
  | `max-output-tokens` | `is_error:true`、`stop_reason:"max_tokens"`、`error_code:"max_output_tokens"`（**string**）、`errors:["The model reached its output token limit and the response is incomplete. Please try again or break the task into smaller parts."]`、`result:""` | 1 |
  | `auth-failed` | `is_error:true`、`error_code:"authentication_failed"`、`result:""` | 1 |
  | `semantic-unknown` | `is_error:true`、`error_code:"rate_limit"`、`errors:["…"]`、`result:""` | 1 |
  | `resume-failed` | `is_error:true`、`error_code:"invalid_request"`、`errors:["No such session: resume not found"]`、`result:""` | 1 |
  - `resume-failed` 供 4.1 / 5.1 验证续接降级；`semantic-unknown` 供需求 1.7 的告警日志验证。
  - 沿用现有 `FAKE_QODER_MODE` 环境变量开关与 `default` 分支（退出码 2），既有 mode 全部保留。
- 单测委托 `unit-test` skill，覆盖设计 8.2 的 `bridge/qoder.ts` 行；沿用既有测试的 `diagnosticDir` 注入与 fake bin 方式。

## 验收标准

- `src/bridge/qoder.ts` Lines 覆盖率 ≥ 95%。
- `quota-110`：`ok=false`、`errorKind='exit'`、`errorClass='model_quota'`、`errorCode='110'`、`error` 含"模型额度已用尽"且**不含**英文原文、`errorDetail` 等于 `errors[0]`。
- `max-output-tokens`：`errorClass='output_limit'`、`error` 含"回答被截断"——**需求 2.1 的核心断言：不得判为 `ok=true`**。
- `auth-failed`：`errorClass='auth'`、`errorCode='authentication_failed'`、`error` 含"凭据已失效"且不含 `authentication_failed` 字样。
- `semantic-unknown`：`errorClass='unknown'`、`errorCode='rate_limit'`、`error` 为一期 `exit` 文案（`执行失败：qodercli 异常退出（退出码 1）。详见本机日志。`）。
- 四类传输层失败（`timeout` / `spawn` / `empty` / `parse`）的 `errorClass` 均为 `'unknown'`，`error` 文案与一期逐字相同。
- 诊断文件 header 含 `# errorClass:` / `# errorCode:` 且值正确。
- 一期用例全部保持绿：5MB 缓冲上限、261KB stderr 不进提示、`parseResult` 尾部解析、宽限期强制落定、`cleanEnv`。
