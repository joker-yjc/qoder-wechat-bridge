# 1.4 互斥集成验证

- 所属任务组：T1. 实例互斥
- 硬前置：1.3

## 目标

用假 iLink 与真实临时文件系统做端到端验证，证明三个高风险场景都被兜住：同目录双实例、脏锁接管、同 bot 跨状态目录。

## 实现要点

- 复用 `test/helpers/fake-ilink.ts` 与临时 `QWB_CONFIG_DIR` / `QWB_STATE_DIR`，每个用例独立目录。
- 场景 1：同一状态目录启动两个 `runService`，第二个必须拒绝（抛 `AlreadyRunningError`），第一个仍能处理一条消息并正常回复。
- 场景 2：预写 `run.lock` 为不存在的 pid（如 `999999`），`runService` 应清理并成功启动。
- 场景 3：两个临时状态目录、同一 `botId`，第二个必须拒绝；不同 botId 互不影响（可作为反例断言）。
- 场景 4：spawn 两个真实 Node 子进程（`test/fixtures/instance-lock-contender.mjs`，经 Vite SSR 加载 TS 源码）抢同一 `stateDir`，断言恰好一个 exit 0、另一个 exit 1 且输出含「已在运行」——这是需求 2.1 的跨进程证据。
- 隔离：`beforeEach` 将 `HOME` 指向临时目录（`globalInstancesDir()` 走 `os.homedir()`），用例结束后 `instances/` 与临时目录均无锁残留。
- 每个用例结束后 stop 服务并断言锁文件已删除；失败路径也要清理，避免污染后续用例。

```bash
npx vitest run test/integration/instance-lock.test.ts
```

## 验收标准

- 四个场景全部通过；
- 第二个实例不产生任何微信消息（用 fake iLink 的 `sent` 断言）；
- 用例结束后临时目录与临时 `HOME` 的 `instances/` 均无残留 `run.lock` / bot 锁。
