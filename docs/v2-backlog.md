# v2+ 待办

v0.1 刻意砍掉的东西。每条都标了为什么当时不做、以及做之前要确认什么。

## 双向决策（v0.3）

`notify` 是单向的：发出去就不管了。真正需要"等你回一句再继续"时，要解决单消费者问题：

- `getUpdates` 只能有一个进程持有游标，任务侧和守护进程不能同时收消息。
- 设计方向：任务调用 `qoder-wechat ask "问题" --timeout 10m`，写入 `pending-questions.jsonl`；守护进程在下次入站时识别"该用户有待回答问题"，把这条消息作为答案写入 `answers/<id>.json`，而不是当成新任务；`ask` 轮询答案文件，超时返回。
- 需要处理：多个待回答问题、答案与任务的对应关系、超时后的默认动作、任务进程崩溃后的清理。
- 前置：先把 `pending-notifications` 的队列语义稳定下来（v0.2 已具备）。

## 通道与消息类型

- **出站媒体**：已实现 iLink 原生发送（`getUploadUrl` + AES-128-ECB + CDN 上传 + `image_item/file_item/video_item`），图片/文件直接在聊天里显示；**入站图片/文件/视频也已支持**（下载解密 + `--attachment`）。
- **语音**：入站优先用微信转写，无转写会直接提示重发；出站已用 macOS `say` + `silk-wasm` 跑通链路（服务端返回 messageId），但字段与平台入站语音完全对齐后**客户端仍不渲染**，判断官方机器人通道暂不支持出站语音。优先级最低；需要发音频时用 `send-file`。
- **视频**：入站已按文件保存并附带；出站最复杂，优先级最低。

## 交互体验

- **`TOOL_CALL_START/RESULT`（类型 11/12）进度气泡**：官方协议支持，能让长任务"看起来在干活"。做之前要确认客户端的渲染行为与条数是否计入下行额度。
- **流式输出**：`qodercli -o stream-json` 可按事件增量解析；当前实现只取最终 `result`。风险是中间输出会快速耗尽额度，需要节流策略。
- **取消任务**：现在只能等超时。需要 `qodercli` 的取消信号（或 SIGTERM + 会话恢复语义）。

## 会话与路由

- **多会话切换**：按 `/new`、`/use <name>` 管理多个 Qoder 会话。
- **按项目路由**：消息前缀或关键词指定 `cwd`，替代固定目录。
- **群聊**：官方 iLink 通道 `groupPolicy: "disabled"`，只能换通道（企业微信智能机器人或 Web 协议方案），后者有封号风险。

## 可靠性

- **下行额度精确记账**：当前按"每条入站 9 条"保守估算，未处理服务端实际回执的计数。
- **补发去重**：outbox 目前靠发送成功即删除；若发送成功但服务端未送达（`ret=0` 不保证送达），无法察觉。
- **多实例互斥**：同一 token 起两个进程会抢 `get_updates` 游标，需要文件锁。

## 工程

- **测试**：当前只有类型检查。补 `chunkText`、`parseWeixinJson`、路由/额度的单元测试。
- **CI**：GitHub Actions 跑 typecheck + build + pack 自检。
- **发布**：`npm publish` 前需要完整跑一遍真实链路；`@jcyao` scope 已确认可用。

## 明确不做

- 修改 Qoder Desktop 内部 SQLite 去唤起会话（无契约）。
- 依赖 Qoder Desktop 的 `127.0.0.1` 端口（内部服务，随时变）。
- 把插件当作消息入口（MCP 无入站推送）。
